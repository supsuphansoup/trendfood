# 트렌드푸드 인스타·네이버 데이터 조사

1. 우선 후보는 네이버 검색어 트렌드·쇼핑인사이트지만, 광고 수익 서비스의 지수 저장·가공 허용 범위를 먼저 서면 확인해야 한다. [공식 상품 개요](https://guide.ncloud-docs.com/docs/apihub-overview)
2. 블로그·카페·뉴스 검색 결과로 유행 데이터베이스를 만들거나 AI 요약에 넣는 기존 제안은 최신 검색 API 특약에 맞지 않는다. [공식 개정 약관](https://developers.naver.com/notice/article/33400)
3. 검색광고 키워드 도구는 광고 관리 외 사용이 금지되고, 쇼핑 검색 API는 종료됐다. [공식 검색광고 약관 공지](https://ads.naver.com/notice/35066) · [공식 종료 공지](https://developers.naver.com/notice/article/32530)
4. 인스타그램 해시태그·Business Discovery는 심사와 이용 목적 확인 후의 후보이며, oEmbed는 화면 표시 전용이고 연구자용 자료는 우리 상업 서비스에 쓸 근거가 없다. [공식 인스타그램 개요](https://developers.facebook.com/documentation/instagram-platform/overview) · [공식 연구 도구 안내](https://about.fb.com/news/2023/11/new-tools-to-support-independent-research/)
5. 다음 행동은 네이버에 저장·상업 이용을 문의하고, Meta에는 음식 유행 분석 목적과 사업자등록 없는 팀의 인증 가능성을 문의하는 것이다. 앱·계정·키 생성이나 신청은 이번에 하지 않았다.

## 조사 기준과 기존 구성안에서 달라진 점

- **확인일: 2026-11-10.** 아래 모든 표의 확인일도 같다. API는 프로그램이 데이터를 요청하는 공식 창구다. 공개 게시물이라는 이유만으로 저장·분석·재배포까지 허용되지는 않는다.
- 읽은 내부 기준: `reports/트렌드푸드 데이터 연동 구성안.md`, `docs/intent.md`, `docs/spec.md`의 수집 규칙·Compliance·미결 항목, `docs/plan.md` 1단계. 인스타그램 항목의 실제 위치는 Open questions 11이 아니라 **Areas of concern 11**이다. 기존 문서는 수정하지 않았다.
- 우리 조건은 학생 팀·개인 계정·사업자등록 없음·0원 운영 목표·쿠팡/애드센스 수익·정적 사이트와 GitHub Actions 하루 1회 수집이다. 따라서 ‘비영리 연구’와 다르다. `trendfood.pages.dev`는 있지만 개인정보처리방침 본문은 비어 있다.
- 기존 구성안의 주요 보완점은 **검색 API의 2026년 9월 특약, 쇼핑 검색 종료, 검색광고 목적 제한, oEmbed 토큰 면제, API HUB 문서 간 숫자 충돌**이다. 이미 정리된 일반적인 키 발급 방법은 되풀이하지 않았다.
- **읽기 제한:** Meta 개발 문서는 직접 열 때 일부 429 응답으로 접근 불가였다. 해당 항목은 Context7에 색인된 공식 문서 본문을 읽었다. 색인의 갱신 시각은 제공되지 않아 현재 앱 화면까지 확인한 것으로 보지 않는다. 네이버 클라우드 일부 페이지는 본문이 표시되지 않아 공식 검색 색인으로 확인했으며 아래에 표시했다. 로그인·API 호출·차단 우회는 하지 않았다.
- 쓸모의 ‘상·중·하’는 **우리의 상업 서비스·예산·수집 방식에 맞는 정도**다. ‘상’도 이용 허가가 확정됐다는 뜻은 아니다. 비용이 ‘미확인’이면 무료라고 판단하지 않는다.

### 해시태그로 실제 받을 수 있는 값과 못 받는 값

`ig_hashtag_search`는 태그의 식별자만 찾는다. 이어서 인기·최근 목록을 요청해야 게시물을 받는다. 응답에는 `id`(게시물 식별자), `caption`(설명 글), `comments_count`(댓글 수), `like_count`(좋아요 수), `media_type`(사진·영상 등), `media_url`(미디어 주소), `permalink`(원문 주소), `timestamp`(게시 시각), `children`(여러 장 게시물의 하위 항목)을 요청할 수 있다. 숨겨진 좋아요 수는 빠질 수 있다. **작성자명 `username`은 요청할 수 없으며 조회 수 필드도 이 목록에는 없다.** 인기 판정에 조회 수가 쓰인다는 설명과 조회 수를 API가 준다는 주장은 다르다. [공식 필드 목록](https://developers.facebook.com/documentation/instagram-platform/instagram-graph-api/reference/ig-hashtag/top-media) — 확인 2026-11-10.

30개는 요청 30회가 아니라 **서로 다른 태그 30개**다. 같은 태그를 7일 안에 다시 조회해도 새 칸을 차지하지 않고 최초 조회의 7일 시계를 다시 시작하지도 않는다. 최근 목록은 직전 24시간이며 시간순 정렬을 보장하지 않는다. 하루 1회 수집은 실행 지연·실패 시 놓치는 글이 생길 수 있다(이 문장의 운영상 판단). 기존 자료의 ‘최근 250개’를 현재 총량으로 확인할 공식 근거는 찾지 못했다. **50개는 페이지당 최대값**이라 전체 수집 보장량이 아니다. [공식 태그 한도](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-facebook-login/hashtag-search) · [공식 최근 목록](https://developers.facebook.com/documentation/instagram-platform/instagram-graph-api/reference/ig-hashtag/recent-media) — 확인 2026-11-10.

해시태그·Business Discovery에는 일반 계정 API의 ‘노출 수 × 4,800/24시간’ 공식을 그대로 적용하면 안 된다. 공식 개요는 두 기능을 **Platform Rate Limits**로 분리한다. 일반 플랫폼 문서에는 앱 토큰의 시간당 호출 수를 ‘200 × 앱 이용자 수’로 설명하지만, 이를 사용자 토큰으로 조회하는 우리 팀의 확정 한도로 단정할 수 없다. 앱 화면과 실제 응답 헤더를 나중에 확인해야 한다. [공식 구분](https://developers.facebook.com/documentation/instagram-platform/overview) · [플랫폼 제한 설명](https://developers.facebook.com/docs/graph-api/advanced/rate-limiting) — 확인 2026-11-10.

### 심사 전에 우리 팀이 준비해야 할 것

공식 안내의 순서는 기능을 보여 줄 수 있는 앱, 권한별 목적 설명과 화면 녹화, 심사자가 따라 할 단계와 필요한 계정, 공개 개인정보처리방침, 데이터 삭제 방법 등이다. 권한만 신청하고 사용 화면을 보여 주지 못하는 상태로는 준비가 끝난 것이 아니다. **현재 빈 개인정보처리방침은 먼저 채워야 한다.** 삭제 안내는 URL 또는 처리 콜백으로 제공하는 경로가 있어 정적 사이트라는 이유만으로 자동 탈락이라고 볼 수는 없다. 다만 실제 삭제 접수·처리 방법이 있어야 한다. [인스타그램 앱 준비](https://developers.facebook.com/docs/development/create-an-app/instagram-use-case) · [Threads 앱 준비](https://developers.facebook.com/documentation/threads/get-started/create-an-app) — 확인 2026-11-10.

Advanced Access에는 사업체 인증이 요구된다. Meta 일반 문서의 인증 서류 예에는 사업 허가·설립 증명, 사업체 이름·주소·전화 확인 자료가 있다. **전문 계정 전환이나 개인 신원 인증만으로 사업체 인증을 대신한다고 볼 수 없다.** 사업자등록이 없는 우리 팀은 현재 증빙 경로를 확보하지 못했다. 다만 한국에서 사업자등록증이 유일한 허용 서류인지, 이 앱에 다른 인증 경로가 허용되는지는 확인하지 못했으므로 ‘개인은 무조건 불가’라고 단정하지 않는다. [공식 사업체 인증](https://developers.facebook.com/docs/development/release/business-verification) · [공식 서류 예시: 다른 Meta 제품의 공통 인증 안내](https://developers.facebook.com/docs/threat-exchange/getting-access) — 확인 2026-11-10.

유료 개인 도메인 구입이 모든 심사의 필수 조건이라는 공식 근거는 확인하지 못했다. 우선 `trendfood.pages.dev`에서 서비스 설명·개인정보처리방침·삭제 안내가 공개되고 앱 설정 주소와 맞아야 한다. 사업체·도메인 소유 확인이 추가로 요구되면 그때 제출 조건을 확인해야 한다. **도메인만 구입하면 사업체 인증이나 앱 승인이 해결되는 것은 아니다.** [공식 앱 설정 안내](https://developers.facebook.com/documentation/threads/get-started/create-an-app) — 확인 2026-11-10.

심사에서 더 큰 쟁점은 목적이다. Instagram Public Content Access의 공식 허용 예는 자사 해시태그 캠페인, 브랜드 반응 분석, 이벤트 참가자 확인, 고객 지원·자사 이용자 이해다. **전국 음식 유행 순위를 만들어 광고 수익을 얻는 목적이 여기에 포함되는지는 미확인**이다. 이 사실을 그대로 설명해 사전 문의해야 하며 자사 캠페인이라고 바꿔 적으면 안 된다. [공식 허용 목적](https://developers.facebook.com/documentation/instagram-platform/overview) — 확인 2026-11-10.

공식적으로 보장된 심사 기간이나 신규 학생 서비스의 통과율은 찾지 못했다. **둘 다 미확인**이다. 비공식 사례로 2026년 Reddit에는 심사 화면이 약 20일을 안내했다는 글이 있고, 개인 개발자의 글에는 본인 계정 테스트에서도 IPCA 심사가 걸린 사례가 있다. 기간·성공률의 통계로 쓰면 안 된다. [비공식: 기간 사례](https://www.reddit.com/r/facebook/comments/1u1h6rl/meta_app_review_now_takes_20_days_heres_what/) · [비공식: 개인 개발 사례](https://note.com/syumy_taro/n/n6521a2e1cd19) — 확인 2026-11-10.

### 표시·저장과 종료된 경로

- oEmbed는 현재 기본 토큰 없이 표시할 수 있지만, **공식 문서 간 시작 날짜 충돌**이 있다. Instagram 변경 이력은 **2026-05-15**, 일반 Graph oEmbed 문서는 **2026-06-15**라고 쓴다. 현재 토큰 면제 여부는 일치하지만 정확한 전환일은 미확인이다. 작성자·썸네일 관련 필드도 2025-11-03 삭제 이력이 있어 예전 응답 예시를 그대로 쓰면 안 된다. [공식 Instagram 변경 이력](https://developers.facebook.com/documentation/instagram-platform/changelog) · [공식 일반 oEmbed](https://developers.facebook.com/docs/graph-api/reference/oembed-post) — 확인 2026-11-10.
- 해시태그·Business Discovery에서 `media_url`을 받는 것은 사진을 우리 서버에 저장하거나 저작권을 넘겨받는 허가가 아니다. 팀의 플랫폼 사진 저장 금지 규칙을 유지한다. 이들 API의 텍스트·수치·파생 점수별 보관 기간과 삭제 반영 의무는 이번 조사에서 확정하지 못했다. **다른 플랫폼의 30일 규칙을 임의로 적용하지 않는다.** [기능별 공식 개요](https://developers.facebook.com/documentation/instagram-platform/overview) — 확인 2026-11-10, 보관 조건은 미확인.
- Meta Content Library도 제한 없는 공개 데이터 덤프가 아니다. SOMAR 환경은 삭제 대상 ID를 주기적으로 확인하고 삭제하도록 요구한다. API 자료를 외부 서비스로 반출할 수 있는 범위는 별도 확인 대상이다. [공식 운영기관 안내](https://www.icpsr.umich.edu/sites/somar/meta-content-library) — 확인 2026-11-10.
- **Instagram Basic Display API는 2024-12-04 종료**, **CrowdTangle은 2024-08-14 이후 이용 불가**다. 이를 새 무료 공개 수집 경로로 제안하지 않는다. [공식 Instagram 변경 이력](https://developers.facebook.com/documentation/instagram-platform/changelog) · [공식 CrowdTangle 종료 안내](https://about.fb.com/news/2023/11/new-tools-to-support-independent-research/) — 확인 2026-11-10.
- EU 디지털서비스법(DSA)에 따른 연구자 데이터 접근도 상업 서비스용 우회 경로가 아니다. 공개 데이터 접근 연구자는 상업적 이해관계에서 독립적이고 EU의 구조적 위험 연구 등 법의 목적을 충족해야 한다. [공식 규제기관의 연구자 접근 안내](https://www.cnam.ie/app/uploads/2025/12/DSA-Article-40-Data-Access_-Frequently-Asked-Questions.pdf) — 확인 2026-11-10.

### 검색 결과를 저장·가공해도 되는가

**기존 구성안의 ‘블로그·카페 결과 수와 단어를 모아 유행 점수를 만든다’는 제안은 채택하면 안 된다.** 개발자센터 검색 API 특약은 2026-09-07부터 검색 결과 표시 목적으로 한정하고, 원형·출처·링크를 유지하도록 한다. 저장·캐싱은 원칙적으로 금지되며 **가공·파생물도 데이터에 포함**한다. AI 입력·학습·개선·평가·노출, 검색 결과 페이지의 광고 및 검색 API를 이용한 수익도 금지한다. ‘개인정보를 지웠다’, ‘내부 정렬에만 쓴다’는 이유로 예외가 되지 않는다. [공식 특약 2.1~2.3](https://developers.naver.com/notice/article/33400) — 확인 2026-11-10.

특약 2.4의 임시 보관 예외는 서비스 연속성을 위한 것이다. 기기 장애 대응·개인화는 **24시간 또는 새 질의 중 짧은 기간**, 서버 이력 조회는 **최대 21일**이며 개인화는 기기와 같은 짧은 기간이다. 기간이 끝나면 지워야 한다. **21일치 음식 유행 DB를 만들라는 허용이 아니다.** 카페글 API가 공식 경로인 것과 우리의 커뮤니티 유행 분석 목적이 허용되는 것은 별개의 문제다. [공식 특약 2.4](https://developers.naver.com/notice/article/33400) — 확인 2026-11-10.

HUB도 2026-09-20 시행 개정 공지에서 같은 검색 목적·가공/보관·광고 제한 문구를 공식 검색 색인으로 확인했다. 다만 직접 열면 본문이 표시되지 않았고, **2026-10-07 시행 추가 개정 공지의 존재도 확인했으나 그 전문은 확인하지 못했다.** 따라서 위 조항을 HUB의 최종 전문 전체를 검토한 법률 판단으로 읽으면 안 된다. 현행 전문과 우리 사례의 허용 여부는 네이버에 서면 확인해야 한다. 확인 전에는 기존 분석 제안을 승인된 것으로 취급하지 않는다.
