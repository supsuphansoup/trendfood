# 모든 음식에 실사·생성 예시 이미지 연결

- 날짜: 2026-11-13
- 누가: Codex
- 관련: docs/spec.md R1·R4·R14 / docs/design.md / docs/automation.md

## 한 것

- 팀장의 “텍스트 카드 대신 실사든 생성형이든 맛있어 보이는 사진” 요청에 따라 이전 AI 사진 금지·텍스트 카드 우선 기준을 변경했다.
- 내장 `image_gen` 도구로 음식별 이미지를 한 장씩 총 26장 생성했다. CLI/API 대체 경로는 사용하지 않았다. 생성 결과를 직접 확인하고 레시피의 주요 재료·조리 형태에 맞춰 적용했다. 두바이 쫀득쿠키는 얇은 코코아 마시멜로 겉피와 피스타치오·카다이프 단면을 표현했다.
- 기본 생성 위치의 PNG 원본을 보존하고 프로젝트에 1200×800 WebP로 변환 저장했다. 총 약 3,885KB, 장당 92~208KB. 현재 공개 JSON은 실사 4개·생성 예시 26개·준비 중 0개다.
- 생성 예시는 카드 배지·상세 소개·이미지 안내·대체 설명에서 구분한다. 완제품 3종은 실제 상품과 모양·구성·크기가 다를 수 있는 예시로 명시했다. 실사 출처·작가·CC 라이선스를 만들어 붙이지 않았다.
- 생성 번들을 실사 번들과 분리해 `photos:sync`가 연결을 지우지 않도록 했다. 생성 이미지의 음식 주소 불일치와 AI 설명 누락은 콘텐츠 검증에서 거절한다.

- 기존 화면은 `TF_SEED_ONLY=1`, `TF_CONTENT_ONLY=0`, 가짜 Supabase 환경으로 `npm.cmd run build` 후 3100 포트에서 검사했다. 실제 공개 콘텐츠는 `TF_SEED_ONLY=0`, `TF_CONTENT_ONLY=1`로 빌드 후 3101 포트에서 검사했다.
- 기존 Windows 서버 종료 정지를 피하도록 기존 Playwright 설정을 상속하고 `webServer`만 제외한 임시 설정을 썼다. 서버는 별도 실행 후 모두 종료했다. 임시 설정·로그는 커밋 제외 `web/data/`에 있다.
- 처음 단위 검사에서는 새 import를 모르는 사진 로더 모의 처리와 다른 주소에 기존 생성 이미지를 복사하던 병합 시험이 실패했다. 실제 생성 정보는 불러오고 이미지 로더만 대체하도록 수정했으며, 새 음식 병합 시험은 해당 음식 이미지가 없으므로 pending으로 명시해 최종 126개가 통과했다.
- 첫 콘텐츠 검사에서 광고 자리까지 음식 카드로 잡아 2개가 실패했다. 음식 제목이 있는 카드만 검사하도록 수정하고 최종 8개를 모두 재검사했다. 시간 제한을 늘려 숨기지 않았다.
- 새 생성 이미지 검사 3개: 파일·크기·음식별 고유 연결·프롬프트 보존, 다른 음식/설명 누락 거절, 실제 표시 이미지와 업로드 우선순위. 콘텐츠 브라우저 검사에서 모든 음식 카드 로딩과 26개 생성 표시, 전체 상세 안내를 확인했다. 기존 접근성·가로 넘침·찜·상세 이동 검사도 통과했다.

## 정한 것·남은 것

- 생성형 이미지 허용은 팀장의 이번 명시 요청에 따른 변경이다. 별도 확인은 요청하지 않았다. 스타일은 따뜻한 자연광·중립 배경·음식 중심 3:2 구도로 맞췄다. 새 패키지를 추가하지 않았다.
- 내장 생성 도구를 대화에서 실행한 것이며 GitHub 예약 이미지 생성 API를 연결한 것은 아니다. 미래의 새 음식까지 생성 이미지를 자동 공급하려면 별도 API·비용 한도·결과 검사를 연결해야 한다. 실사 자동 검색은 유지하며 기존 생성 이미지를 자동 덮어쓰지 않는다.
- 전체 이미지 회귀 검사는 pending이 있는 변경의 저장·배포를 막는다. 신규 음식에 적합한 실사가 없으면 해당 실행의 새 콘텐츠 자동 반영은 보류된다. 예약 생성 미연결을 숨기거나 완전 자동 생성으로 보고하지 않는다.
- 현재 환경은 `.git` 쓰기 제한으로 커밋·push·실제 사이트 배포를 하지 못했다. 로컬 파일과 정적 빌드만 갱신했다. 기존 미추적 `.claude/`와 이전 작업 변경은 보존했다.
