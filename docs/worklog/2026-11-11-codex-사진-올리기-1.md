## 한 것
- `photos` 표의 제약·공개 읽기·관리자 쓰기 RLS 와 공개 WebP 전용 `food-photos` 버킷(1MB), 관리자 추가·삭제 정책을 새 마이그레이션에 작성했다. 기존 마이그레이션과 `foods`·`published_foods` 는 바꾸지 않았다.
- 관리자 사진 구역에서 번들 사진과 최근 올린 사진 100개를 고르고 공개 저장소 주소로 미리 볼 수 있다. 사진 ID 를 음식에 저장할 때 기존 히어로 초기화 규칙을 유지했다.
- 파일·출처·라이선스·원본 주소·사용 확인을 검사하고 canvas 로 긴 변 1600px 이하 WebP 로 다시 그린다. 품질 0.82 → 0.7 → 0.6 순서로 1MB 이하를 시도하며 원본을 그대로 올리지 않는다.
- 저장소 업로드 후 사진 정보 추가가 실패하면 해당 파일을 지운다. 성공하면 목록을 다시 읽고 새 사진을 선택하며, 음식 적용은 별도의 [사진 저장]으로 한다.
- 사진 표 조회 실패 시 SQL 안내와 기존 번들 선택·저장을 유지한다. AI 사진 미사용 결정, 이번 완료 범위와 다음 작업, 최초 SQL 순서와 사진 운영 방법을 문서에 반영했다.

## 정한 것·남은 것
- 지시 범위 밖 임의 결정 없음. 크기 계산은 반올림해 3000×2000 원본을 1600×1067 로 만든다. 목록 날짜는 한국 시간의 월/일이다.
- 실제 Supabase 는 호출하지 않았다. 로컬 `psql` 과 PGlite 가 없어 SQL 자체는 직접 실행하지 못했다. 감독자가 PGlite 로 트랜잭션 2회 실행과 제약·RLS 를 검증해야 한다.
- RLS 확인 방법: anon·비운영자 authenticated 는 `photos` select 만 허용하고 insert/update/delete 는 막히는지, 운영자는 모두 가능한지 확인한다. `storage.objects` 는 `food-photos` 에 대한 운영자 select/insert/delete 만 허용하고 anon·비운영자 객체 조회·쓰기·다른 버킷 조회·쓰기·update 는 막히는지 확인한다. 공개 주소의 파일 읽기는 공개 버킷 설정으로 허용한다. 버킷 설정은 public=true·1048576 bytes·image/webp 만인지 확인한다.
- 실제 Supabase 에 `0004_photos.sql` 적용은 사람이 직접 해야 한다. 공개 화면의 빌드 시 사진 내려받기·출처 표시는 다음 2/2 작업이다.
- 사진 삭제 UI 는 이번 범위 밖이다. 사용 중인 사진을 지우면 사이트가 깨질 수 있어 참조 확인을 포함한 별도 작업이 필요하다. 이번 파일 삭제는 표 저장 실패 시 방금 올린 파일을 정리하는 경우뿐이다.
- 새 npm 패키지는 추가하지 않았다. 커밋·push·브랜치 생성·stash·reset 은 하지 않았다.
- 감독자에게 확인한 근거: 설치된 `@supabase/storage-js/src/packages/StorageFileApi.ts` 의 `remove` 주석은 objects 의 delete·select 권한을 요구한다. [기존 공식 API 문서](https://supabase.com/docs/reference/javascript/v1/storage-from-remove)도 같지만 [현행 삭제 가이드](https://supabase.com/docs/guides/storage/management/delete-objects)는 delete 정책만 예시로 든다. 최초 지시의 insert/delete 정책에 관리자 SELECT 도 필요한지 확인 요청했고 아래와 같이 승인받았다.
