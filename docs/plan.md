# Plan: 유행 레시피 × 재료 커미션 서비스

Status: 초안 · 구현 보류. 기술 스택(Q15)과 spec.md의 Areas of concern이 결정되면 STEP 3-a(Plan 모드)에서 계획을 다시 세우고 이 파일을 덮어쓴다.

## Files that change
기술 스택이 미정이라 코드 파일 경로는 아직 적지 않는다. 지금 있는 것은 문서뿐이다.

| 파일 | 역할 |
| --- | --- |
| `AGENTS.md` | AI가 매번 읽는 프로젝트 설명서 |
| `docs/intent.md` | 기획 — 무엇을, 왜 |
| `docs/spec.md` | 설계 — 어떻게 보이고 동작하는가 |
| `docs/plan.md` | 구현 계획 (이 파일) |
| `docs/questions.md` | 결정 대기 질문 |

스택 확정 후 생길 영역(예상): 레시피 데이터, 첫 화면, 레시피 상세(인분·재료 선택), 장바구니 연동, 좋아요·리뷰 저장소, 수수료 표기 공통 요소.

## Order of work
0. **검증 먼저 (코드 전)**: 후보 제휴사에서 여러 상품을 장바구니에 한 번에 담을 수 있는지 조사·실험하고 결과를 questions.md Q1에 적는다. 안 되면 intent부터 고친다.
1. **STEP 0 준비**: 스택 확정 → 프로젝트 초기화 → 빌드 확인 → 커밋. docs/가 이미 있으므로 초기화 위치에 주의 (Q16).
2. 레시피 데이터 구조 + 샘플 레시피 3개 (R1)
3. 레시피 상세: 글 위주 표시 + 인분 조절 (R2, R5)
4. 재료 선택 + 구매 개수 (R6, R7)
5. 장바구니 일괄 담기 + 수수료 표기 (R8, R9)
6. 첫 화면: 유행 순위 (R3)
7. 좋아요 + 좋아요 순위 (R11, R4)
8. 익명 리뷰 + 운영자 삭제 (R10, spec Areas of concern 3)
9. 배포 전 코드 리뷰 → 배포

핵심 흐름(2~5)을 먼저 끝내서 "레시피 → 장바구니"가 실제로 되는지부터 확인한다.

## Risks
- 장바구니 일괄 담기 불가 → 핵심 기능이 바뀜 (0단계에서 먼저 확인)
- 제휴사 링크·API 정책 변경, 제휴 가입 승인 지연
- 인분 계산의 반올림·단위 오류 (분수, "약간" 같은 비수치 양)
- 로그인 없는 좋아요·리뷰의 조작·스팸
- 기존 `index.html` 데모와 새 구조가 섞임 (Q16)
