## 실행과 반영 조건

GitHub Actions `pipeline`이 한국 시간 매일 10:17에 한 번 실행된다(`17 1 * * *`, UTC). 음식 수집·사진 확인·검사·배포를 같은 실행에서 처리한다. GitHub 예약은 지연될 수 있으며 공개 저장소가 60일 무커밋이면 중지될 수 있다. Actions의 `Run workflow`로 즉시 실행할 수도 있다.

이 시간은 방문자 통계로 입증한 최적값이 아니라 현재 수집 구조에 맞춘 운영 선택이다. 검색 추이 종료 날짜를 UTC 기준 전날로 계산하므로 한국 시간 09:00 이후에 실행해야 한국 달력의 전날을 요청한다. 오전 10시대에 시작해 점심 전 검증·배포 여유를 두며, [GitHub 공식 안내](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)에 따라 매시 정각을 피한다. 네이버 공식 API 문서는 정확한 일별 데이터 갱신 시간을 보장하지 않으므로 이 시각에 전날 데이터가 모두 제공된다고 단정하지 않는다.

1. YouTube 공식 API로 최근 7일 최신 영상을 `신상 디저트 먹방`·`편의점 신상 먹방`·`요즘 유행 음식`·`카페 신메뉴 리뷰`의 4개 검색어에서 찾는다. 기존 음식과 등록 별칭을 제외하고 최대 3개 후보를 음식명으로 재검색한다(각각 최신순·조회순 2회). 검색은 실행당 최대 10회이며 `PIPELINE_QUERIES`를 지정해도 발견 검색은 앞 4개만 사용한다. 집에서 만드는 음식으로 제한하지 않는다. 모델 비교 모드는 기존 5개 검색어·10회 검색을 유지한다.
2. 이전에 음식이 확인된 채널을 최대 50개 기록하고 매일 최대 12개를 순환한다. `channels.list`의 공식 업로드 재생목록에서 채널별 최근 항목 10개 중 7일 이내 영상만 읽는다. 첫 실행은 검색으로 추적 채널을 확보하며 다음 실행부터 업로드 추적이 작동한다. Google Trending now 한국 RSS는 음식 관련 제목·뉴스를 최대 10개 보조 힌트로 제공한다. 비음식·사고 뉴스는 거르고 RSS만으로 게시하지 않는다. 채널·RSS 장애는 보고서에 남기고 발견 검색을 계속한다. 추출 입력은 채널과 검색어에 자리를 나눠 최대 70개 제목·힌트로 제한하고 음식명 추출 AI는 1회 호출한다.

4. 공식 `videos.list`의 설명란에서 전체 조리 시간·분량·재료별 사용량·조리 단계가 확인되는 원문 하나를 선택한다. AI의 추출 결과를 실제 설명란과 대조한다. 재료명·사용량·시간·분량·단계의 근거와 숫자가 모두 맞을 때만 레시피를 제공한다. 서로 다른 레시피를 합치거나 조리법을 추측하지 않는다. 완전한 조리법이 없으면 같은 AI 응답에서 음식 소개 인용을 확인한다. 음식명이 포함된 제목·설명란의 연속된 원문 120자·25단어 이내와 출처 ID를 대조하고, 통과하면 `kind=discovery`로 음식 소개만 남긴다. 소개 근거도 없으면 보류한다. 추가 AI 호출은 하지 않는다.
5. 통과한 음식 소개 또는 레시피를 `web/src/data/content/foods.json`에 추가한다. 기존 레시피·주소·사진·확인 날짜는 바꾸지 않는다. 새 글에는 확인 날짜·출처·확인한 연도·자동 대조 및 개별 미검수 안내를 붙인다. 연도는 수집으로 확인한 시기이며 최초 유행 연도를 확정하지 않는다. 음식 소개에는 조리법·재료·구매 링크를 만들지 않으며 목록·상세에서 만드는 법·조리 시간·난이도·재료 담기를 표시하지 않는다. 조리법이 확인된 레시피에는 기존 재료 구매 기능을 제공한다. 이미 소개한 음식도 이후 수집에서 상승 근거와 완전한 조리법을 확인하면 같은 주소·사진을 보존해 레시피를 붙인다. 새 음식 확인을 우선하며 소개의 레시피 보강도 기존 실행당 최대 3개 안에서 처리한다. 조리법이 여전히 없으면 기존 소개를 보존한다.
6. 사진 검색 뒤 콘텐츠 검사·lint·typecheck·단위 테스트·모바일/PC 브라우저 검사를 모두 통과해야 음식 JSON·사진 파일·크레딧·번들 목록을 함께 자동 커밋한다. 같은 실행에서 재사용 `deploy` 워크플로를 직접 호출해 그 커밋을 Cloudflare Pages에 배포한다. `GITHUB_TOKEN`의 push는 다른 push 워크플로를 실행하지 않으므로 push만으로 배포를 기대하지 않는다.

## 사진

2026-11-13 팀장 요청으로 Commons에 Openverse·Pexels 공식 검색 API를 추가했다. Openverse는 현재 Flickr의 원문·이미지 CDN으로 확인되는 사진만 처리하며 CC0·퍼블릭 도메인·CC BY 4.0·CC BY-SA 4.0 조건을 유지한다. 색인의 라이선스 이름·버전·URL·작가·원문/파일 ID·해상도·성인물 여부를 검사하고, 임의 호스트는 내려받지 않는다. Openverse 색인이 원작자의 현재 이용 조건까지 보장하는 것은 아니다. Pexels는 별도의 Pexels License로 처리하며 원문·파일 ID·작가를 보존하고, 푸터의 Pexels 링크와 상세의 사진·작가·라이선스 링크로 출처를 표시한다. Pexels 사진을 CC 라이선스로 바꾸어 표시하지 않는다.

`PEXELS_API_KEY`를 저장소의 GitHub Actions Secret에 등록하면 예약 작업에서도 Pexels를 사용한다. 키가 없으면 Commons·Openverse만 검색하며, 키는 Pexels 검색 API에만 전송하고 파일 다운로드·AI 입력·실행 보고서에 넣지 않는다. 한 검색처의 연결/한도 오류는 다른 검색처를 막지 않으며 `data/photo-report.json`의 `sources`는 설정 여부, `searchWarnings`는 검색 실패 출처를 기록한다. 키가 없거나 실제 호출이 실패한 출처를 연결 완료로 판단하지 않는다.

검색어는 음식별 최대 3개, 출처·검색어 후보를 번갈아 선택해 최대 6장의 실제 이미지만 대조한다. 기존 최대 3장보다 판별 호출이 늘 수 있다. 검토에서 내린 자동 사진도 출처는 재사용하지 않으며, 다른 적합 사진을 확보하면 `photo-auto-<slug>-2`처럼 새 키로 저장해 제외 이력을 덮어쓰지 않는다.

2026-11-13 추가 요청으로 현재 음식은 텍스트 카드 대신 실사 또는 생성 이미지를 보여준다. 적합한 실사 4개를 유지하고, 준비 중이던 26개는 대화의 내장 `image_gen`으로 개별 생성해 연결했다. `web/src/data/content/generated-images.json`에 음식 주소·도구·생성일·최종 프롬프트·안내를, `web/src/assets/generated/`에 1200×800 WebP 파일을 보존한다. `web/src/lib/generated-photos.ts`는 실사 번들과 분리하므로 `photos:sync`가 생성 파일 연결을 덮어쓰지 않는다. 카드·상세·alt에 AI 생성 예시를 표시하고 실제 제품 또는 직접 조리 사진으로 표시하지 않는다. 해당 26개는 레시피를 바탕으로 생성했다. 이후 공개 라이선스 사진을 참고한 변환 예시는 해당 이용 조건을 생성 등록부에 별도로 기록한다.

이번 생성은 대화에서 수행했으며 GitHub 예약 생성 API를 추가하거나 연결한 것은 아니다. 2026-11-13 팀장이 실사 우선 방식을 승인해, 생성 예시가 연결된 음식도 실사 검색 대상으로 바꿨다. 등록부의 음식 주소와 일치하는 생성 이미지만 대상으로 삼고, 기존 실사나 운영자 업로드 사진이 본문·히어로에 있으면 보존한다. 실사가 모든 검증을 통과하면 본문 사진을 교체하고 이전 생성 히어로를 해제한다. 검색·다운로드·판별에 실패하거나 적합한 실사가 없으면 생성 이미지와 안내를 그대로 유지한다. 교체 후에도 생성 파일·프롬프트 기록은 보존한다. 실행 보고서의 `accepted[].replacedGenerated`와 `deferred[].retainedGenerated`로 실제 교체와 기존 예시 유지를 구분한다.

전체 이미지 검사는 `pending`이 있는 변경의 게시를 막으므로, 새 음식에 실사도 생성 예시도 없으면 자동 반영은 보류된다. 모든 새 음식에 생성 이미지까지 자동 공급하려면 별도 예약 생성 API·비용 한도·결과 검사를 연결해야 한다. 예외 데이터의 사진 없는 텍스트 표시 코드는 남아 있지만 현재 공개 JSON에는 대상이 없다.

새 음식은 `pending`으로 시작하고, 같은 예약 작업에서 `npm run photos:auto`가 새 음식·기존 준비 중 사진·생성 예시의 실사를 찾는다. 기본 하루 5개 안에서 빈 사진을 우선하며, 빈 사진과 나머지 생성 예시는 각각 UTC 날짜 단위로 순환한다. 일일 검색 개수나 음식별 최대 6장 판별 한도는 늘리지 않는다. Actions 수동 실행의 `photos_only=true`, `photo_limit=20`으로 음식 수집 없이 최대 20개를 한 번에 확인할 수 있다.

Commons 공식 검색·이미지 정보 API에서 한국어·영어·통용 이름으로 찾는다. 코드가 CC0·퍼블릭 도메인·CC BY 4.0·CC BY-SA 4.0 표시와 해당 라이선스의 공식 URL·작가·출처·별도 제한 없음·해상도를 먼저 확인한다. 비영리·변경 금지 조건이나 알 수 없는 라이선스는 자동 사용하지 않는다. 기존 모델에 실제 사진 바이트와 음식·파일 설명을 함께 보내, 같은 메뉴·실제 사진·가림 없음·메타데이터 일치가 모두 참이고 모델의 신뢰 응답이 0.95 이상일 때만 적용한다. 이 값은 정확도 보장이 아니다. AI 판별 오류가 있을 수 있으므로 자동 대조·개별 미검수 안내와 원문 링크를 표시한다. 다른 속재료·브랜드·제품·그림·AI 생성·간판·확신할 수 없는 사진은 보류한다.

통과한 사진은 크기·형식을 WebP로 바꾸어 저장한다. 제목·원문·작가·이용 조건·라이선스 링크·추가 저작자 표시·확인 날짜·Commons 문서 ID·원본 SHA1을 `web/src/data/content/auto-photo-credits.json`에 보존하고 실제 콘텐츠와 번들 import 목록을 함께 바꾼다. 상세 페이지에 제목·작가·원본·라이선스 링크·변환 안내를 표시하고, CC BY-SA 변환본은 원본과 같은 라이선스로 제공한다. 사이트 자체 글의 복사 제한을 이 사진들에 적용하지 않는다. 원본 SHA1은 Commons 원본의 식별값이며 변환본의 해시는 아니다. 기존 실사·조리법·출처 확인 날짜는 바꾸지 않고, 같은 사진을 다른 음식에 재사용하지 않는다. 검색·다운로드·판별 실패와 적합한 사진이 없는 경우는 기존 생성 예시 또는 준비 중 상태를 보존해 다음 실행에서 다시 확인한다. AI 한도 오류는 새 사진 파일을 쓰기 전에 전체 실패로 처리한다. 실사 검색 단계에서는 플랫폼 썸네일·스크래핑·생성 사진을 쓰지 않는다.

2026-11-13 사진 품질 재검토에서 기존 사진 9개를 내렸다. 따뜻한 말차 라떼에 다른 아이스 음료 두 잔을 쓰거나, 기본 크로플에 오레오 크림 사진을 붙이는 등 레시피와 다른 사진과 책상·매대 중심 사진을 제외했다. 사용자 추가 검토에 따라 포장 용기와 주변 여백이 두드러지는 두바이 쫀득쿠키 자동 사진도 제외했다. 이후 위 생성 이미지 요청 당시 로컬 공개 콘텐츠는 실사 4개·생성 예시 26개·준비 중 0개였다. 제외 사유는 등록부의 `rejectedReason`에 보존하며, 해당 키는 공개 콘텐츠 본문·히어로에 다시 사용할 수 없다. 원본 파일·출처·라이선스 기록은 보존한다.

## 매일 추천 갱신 (2026-11-16)

수집에 성공한 날에는 새 레시피가 없어도 대표 음식과 추천 순서를 갱신한다. 기존 수집의 네이버 검색 추이와 음식명·등록 별칭을 재사용하므로 추가 검색·OpenAI 호출은 없다. 일정은 매일 10:17 KST 하루 한 번이며 GitHub 예약 실행은 지연될 수 있다.

사진까지 확보한 신규 음식은 맨 앞에 배치하고 해당 날짜에만 신규로 표시한다. 기존 음식은 검색 상승 배수 1.3 이상인 일치 항목을 점수순으로 우선하며, 같은 대표만 반복되면 다음 추천을 고른다. 쓸 수 있는 상승 신호가 없으면 기존 목록의 첫 음식을 뒤로 보내 순환한다. 같은 날짜 재실행에서는 순서를 다시 돌리지 않는다. 다음 날짜에는 기존 음식의 신규 표시를 해제한다. 신규 검증 기준은 완화하지 않는다.

`foods.json`의 `recommendation`에 추천 날짜·근거(`new`, `trend`, `rotation`)·신규 주소를 저장한다. 레시피 출처 확인 날짜는 보존하며 화면에는 추천 갱신일과 근거를 따로 표시한다. 기존 음식 순환을 새로운 유행이나 실시간 순위로 표시하지 않는다. 최초 적용은 외부 수집 없이 기존 음식 순환으로 시작한다.

`pipeline/run.ts`가 실행 중인 `web/data/recommendation-input.json`에 기존 공개 스냅샷과 수집 신호를 남긴 뒤, 사진 단계 다음의 `node scripts/refresh-recommendations.ts`가 최종 순서를 반영한다. 이 중간 파일은 커밋·실행 아티팩트에 넣지 않는다. 사진이 없는 신규 음식은 이번 공개에서 제외하고 `discovery-state.json`에 원고를 보존한다. 다음 수집에서는 공식 영상 출처의 게시일·다른 제작자 2명·음식명(소개는 인용 원문까지)을 다시 대조한 원고만 복원해 사진을 재검색한다. 원고를 AI로 매번 재생성하지 않는다. 출처가 삭제·변경됐거나 오래됐으면 공개하지 않는다. 기존 음식의 추천·사진 변경은 계속 검사한다. `recommendation-report.json`은 실제 공개 가능한 신규 음식과 사진 보류를, `automation-report.json`은 음식 소개·레시피 원문 검증 통과를 뜻한다. 사진 검색 한도는 늘리지 않는다. 수집이나 사진 단계가 실패하면 추천 갱신을 성공한 것으로 기록하지 않는다.

## 쿠팡 재료 링크

같은 매일 10:17 KST 작업에서 `PIPELINE_AUTO_COUPANG=true`이면 공식 파트너스 검색 API의 실제 상품별 제휴 링크를 재료에 연결한다. 설정·조건·한도·미설정 처리·실제 계정 검증은 [쿠팡 링크 자동화](coupang-automation.md)를 따른다. API 키와 등록 채널 ID가 없으면 건너뛰고 기존 검색 연결을 유지한다. 사진만 실행하는 `photos_only=true`에서는 쿠팡 검색을 하지 않으며, `links_only=true`로 음식·사진 수집 없이 링크만 확인할 수 있다.

## 설정과 중지

GitHub Secrets: `YOUTUBE_API_KEY`, `NAVER_API_HUB_KEY_ID`, `NAVER_API_HUB_KEY`, 선택한 AI 공급자의 키, 기존 Supabase·Cloudflare 키. 값은 채팅·문서·코드에 쓰지 않는다. GitHub Variables는 다음과 같다.

| 이름 | 값·역할 |
| --- | --- |
| `AI_PROVIDER`, `AI_MODEL` | 기존에 선택한 공급자·모델 유지. 자동화에서 모델을 임의 변경하지 않는다. |
| `PIPELINE_AUTO_PUBLISH` | `true`는 자동 대조·반영. `false`면 기존 후보 수집만 계속한다. |
| `PIPELINE_AUTO_PHOTOS` | 기본 활성. `false`면 사진 자동 검색·적용만 중지한다. |
| `PIPELINE_AUTO_COUPANG` | `true`이면 쿠팡 링크 자동 연결. 키·등록 채널 ID 미설정 시 건너뛴다. `false`면 링크 자동화만 중지한다. |
| `COUPANG_SUB_ID` | 파트너스 계정에 미리 등록한 채널 ID. 음식 slug를 임의로 사용하지 않는다. |
| `TF_CONTENT_ONLY` | `1`이면 출처 확인 JSON이 공개 페이지의 원본이다. |

공개 JSON 모드에서 `TF_CONTENT_ADMIN=1`을 켜면 게시 관리와 재료 링크 탭이 공개 음식 전체를 읽는다. 관리자가 저장한 항목은 Supabase에 보관하고 [사이트에 반영]을 누른 뒤 정적 빌드에서 최신 JSON에 적용한다. 숨김·초안은 홈, 상세 주소, 사이트맵에서 함께 제외하고 관리자에서 다시 공개할 수 있다. 출처·유행 기록과 자동 수집 원본은 JSON 또는 아래 `content:import`로 관리한다. 공개 목록의 재료는 사용량과 쿠팡 주소를 관리한다.

운영 연결은 Supabase SQL Editor에서 `web/supabase/migrations/0005_content_edits.sql`을 적용한 뒤 GitHub 저장소 변수 `TF_CONTENT_ONLY=1`, `TF_CONTENT_ADMIN=1`로 `deploy`를 실행한다. 빌드는 공개 확정본만 읽고, 관리자 저장본과 내림 사유는 RLS로 운영자에게만 제공한다. [사이트에 반영]에서 확정 저장 뒤 배포 요청에 실패하면 다음 배포에서 적용되며, 버튼으로 재요청할 수 있다. 변수가 꺼져 있으면 게시 관리는 기존 Supabase 경로를 사용한다.

공개 JSON을 관리하는 운영자는 후보 큐에서 확인한 출처 주소로 후보를 승인해 게시 관리에 초안을 만들 수 있다. 이어서 [게시하기]와 [사이트에 반영]을 누르면 다음 정적 배포에서 공개한다. 자동 수집 기록은 원문 검증을 통과한 원고 수와 사진 미확보 건수를 보여 준다. 공개 완료 수는 현재 배포본에 실린 해당 날짜의 신규 음식 수다.

`pipeline` 실행 요약과 14일 보관 `automation-report` 아티팩트의 `automation-report.json`·`photo-report.json`에 적용 가능 항목·사진 출처·보류 이유가 나온다. 설명란 원문·내부 근거 인용·이미지 바이트는 보고서에 저장하지 않는다. 개별 음식의 설명란 조회·근거 검증 실패는 그 음식을 보류한다. 수집 전체·AI 한도·검사 실패 시 새 커밋을 만들지 않는다. 배포 실패 시 기존 사이트는 유지되고 새 데이터 커밋은 남으므로 Actions의 `deploy`를 다시 실행한다. 수집 중 main이 바뀌면 반영을 중지하고 다음 실행에서 다시 시도한다.

### 실사 우선·참고 사진 또는 검증된 설명 기반 자동 생성 (2026-11-23)

사용자 요청으로 정규 사진 작업에 OpenAI Images API를 연결했다. 실사 검색은 음식 최대 5개·음식당 후보 최대 6개를 유지한다. 같은 검색에서 실제 음식·메타데이터·레시피 일치와 신뢰도 0.95 이상을 통과했으나 구도가 부적합한 사진을 생성 참고로 우선 사용한다. 추가 요청에 따라 정확한 참고 사진이 없거나 검색이 실패해도 원문 검증된 음식 이름·소개·재료·조리법으로 생성한다. 불일치 사진은 참고로 넘기지 않는다. 기존 실사·업로드 사진·생성 예시를 새 생성 이미지로 덮어쓰지 않는다.

신규 원고와 원문을 재확인한 대기 원고를 이번 실행의 인기 점수순으로 함께 비교한다. 점수는 검색 상승 배수 × (1 + log2(영상 언급 수))다. 검색 신호가 없는 대기 원고는 이번에 재확인한 최근 영상의 중복 없는 언급 수와 배수 1로 계산하며 검색 상승을 추정하지 않는다. 잘못된 점수는 쓰지 않고, 동점이면 최근 검증일·음식 주소순으로 고른다. 이 순서는 사진 검색·생성·최종 공개에 공통으로 적용한다. 실시간 전체 시장의 절대 인기 순위를 뜻하지 않는다. 하위 후보 사진이 먼저 준비되어도 상위 후보의 사진 처리를 생략하지 않으며, 한도 안에서 상위 후보의 사진을 확보하지 못하면 다음 후보를 고른다.

Commons에서 이용 조건이 검토 대기인 사진은 실사 후보와 생성 참고에서 제외한다.

생성 예시에 쓸 접시·각도·빛은 요리의 실제 담음새에 맞춘다. 접시 전체보다 음식의 핵심 형태와 질감이 카드와 상세에 살아 있어야 한다. 주요 형태가 잘리거나 과도한 여백으로 음식이 작게 보이는 구도, 균일하게 반복된 재료, 부자연스럽게 매끈한 단면과 그림자는 판별에서 보류한다.

실사 검색을 모두 마친 뒤 빈 대표 사진 최대 3개를 `gpt-image-2`, medium, 1536×1024, n=1로 각각 생성한다. 참고가 있으면 `/v1/images/edits`, 없으면 `/v1/images/generations`를 사용한다. 결과와 음식 설명·조리법을 대조하고 카드·PC·모바일 구도, 형태·속재료·글자·왜곡을 검사한다. 음식 질감·색·그림자에 합성 느낌이 강하면 `naturalAppearance`에서 탈락한다. 실제 참고 사진을 이용할 때는 음식 자체의 특징만 살리고 접시·각도·조명·배치·배경을 새로 구성한다. 결과의 구도가 참고 사진을 재현했으면 `distinctComposition`에서 탈락한다. 설명으로 정확한 음식 일치를 판단할 수 없거나 다른 음식 유형·확인되지 않은 제품 외관이면 거절한다. 품질 검사에서 탈락하면 지적 사유를 프롬프트에 반영해 음식당 한 번 더 생성한다. 한 음식이 끝내 탈락해도 나머지 원고는 계속 처리한다. 모든 조건과 신뢰도 0.95 이상을 통과하면 1200×800 WebP·생성 프롬프트·모델·날짜·생성 근거(`basis=reference|description`)를 별도 등록한다. 설명 기반은 참고 사진이 없다고 명시하며 작가·주소·라이선스를 꾸미지 않는다. 참고 기반만 참고 작가/주소/이용 조건을 보존한다. AI 자동 대조는 사람의 정확한 검수를 보장하지 않는다. 생성 안내와 참고 출처는 상세 하단의 기본 접힌 ‘사진 정보’에 표시하며 대체 설명에도 AI 생성을 명시한다. CC BY/CC BY-SA 참고의 변환본은 같은 이용 조건으로 제공한다.

한국 날짜 기준 하루 **생성 성공 최대 3개·음식당 최대 2회·유료 요청 총 6회**다. 실패·시간 초과·결과 탈락도 차감한다. 품질 탈락만 사유를 반영해 보완하고, API 오류·시간 초과·불명확한 응답·기록 저장 실패는 자동 재시도하지 않는다. Actions는 생성 전에 날짜별 캐시 예약을 저장하고 GitHub 공식 API에서 저장 여부를 확인한다. 확인 실패 시 유료 생성을 건너뛰고 실사 처리만 진행한다. 시도한 날의 예약은 다음 재실행에서도 유료 생성을 중지한다. 단, 현재 실행이 확보한 예약에 한해 정상 완료한 사진 보고서에서 **시도 0회·생성 0개**가 확인되면 공식 API로 반환한다. 원문 검증을 통과한 빈 사진 음식이 없어 호출하지 않은 경우가 당일 생성을 막지 않게 한다. 기록이 없거나 불명확하면 반환하지 않는다. 예약 반환에 실패하면 보수적으로 다음 날까지 보존한다. 기존 하루 1회 설정으로 이미 유료 생성한 날의 예약도 보존하고 다음 날 새 한도를 적용한다. 유료 시도가 있었던 예약 캐시를 사람이 지우면 중복 호출 보호가 사라지므로 지우지 않는다. 로컬은 `data/image-generation-state.json`에 호출 전에 예약을 쓰며, 이 파일을 지우지 않는다. 날짜가 바뀐 새 실행에서 다음 한도를 쓴다. 비용은 생성 토큰·입력 이미지에 따라 달라지며 요청 제한은 달러 단위 상한이 아니다. 기존 음식 검색 10회·원고 생성 3개 한도는 유지하고 이미지 생성 및 결과 판별만 추가한다.

최종 공개도 하루 최대 3개다. 3개는 상한이며 검증된 후보가 없으면 0개를 추가한다. 같은 날짜에 이미 공개한 음식 수를 빼고 남은 자리만 허용하며, 사진까지 확보한 후보 중 인기 점수 상위부터 순서대로 공개한다. 초과 원고는 다음 실행까지 캐시에 보존한다. 사진이 없는 원고는 계속 공개에서 제외한다. `recommendation-report.json`의 `publication`과 Actions 요약에서 기존 필드인 목표 3개·공개 대상 수·부족 건수를 확인한다. 부족 건수는 상한까지의 남은 자리이며, 후보가 없어 추가하지 않은 경우 자체를 오류로 보지 않는다. 이 수는 전체 검사·커밋·배포 전의 공개 대상이며 배포 완료 건수가 아니다. 품질 탈락, API 오류, 전체 검사·배포 실패가 있으면 해당 사유를 보고한다. 음식 수를 맞추려고 검증을 생략하지 않는다. 정규 실행은 매일 10:17 KST 한 번이며 GitHub 예약 지연이 있을 수 있다. 생성·보완·전체 검사를 위해 작업 제한 시간은 60분이다.

기존 `OPENAI_API_KEY`를 사용하며 저장소 변수 `PIPELINE_AUTO_IMAGE_GENERATION=false`로 생성만 중지한다(기본 활성). `PIPELINE_AUTO_PHOTOS=false` 또는 `PIPELINE_AUTO_PUBLISH=false`도 생성을 중지한다. `--dry-run`, `checks_only`, `pending_only`, `links_only`, 모델 비교는 이미지 생성 API를 호출하지 않는다. 이미지 모델 권한·결제·검증된 설명이 없거나 결과가 검사에 탈락하면 보류 사유를 `photo-report.json`에 남긴다. 생성 성공 건수와 근거는 `generated`, 실제 시도와 결과는 `imageGeneration.attempts`에서 확인한다. 사진이 없다는 이유만으로 생성을 생략하지 않지만 새 트렌드·원문 검증·결과 품질·전체 검사를 통과하지 못한 음식은 공개하지 않는다.

`photos_only=true`도 캐시의 사진 대기 원고를 공식 원문으로 재확인한 뒤 동일한 사진 처리·전체 검사·배포를 실행한다. 새 음식 검색·AI 원고 생성·쿠팡 검색을 추가하지 않는다. 검사 전에 원고 캐시를 지우지 않는다. 생성 이미지·등록부·번들·음식 JSON은 검사 후 같은 커밋으로 저장한다.

API 기준: [OpenAI 이미지 편집](https://developers.openai.com/api/reference/resources/images/methods/edit), [이미지 생성](https://developers.openai.com/api/reference/resources/images/methods/generate), [GPT Image 2](https://developers.openai.com/api/docs/models/gpt-image-2). 실제 생성 성공과 배포 여부는 실행 결과에서 별도로 확인한다.

### 생성 예시 사진으로 대기 음식 반영 (2026-11-20)

- 실제 메뉴의 모양·단면을 확인해 대화의 이미지 생성 도구로 예시를 만들고, `src/assets/generated/` 파일·`src/data/content/generated-images.json` 프롬프트/참고 주소·`src/lib/generated-photos.ts` 번들을 함께 등록한다. 실제 참고 사진은 공개 번들에 복사하지 않는다.
- 추천 반영은 음식 slug와 일치하는 등록 이미지가 있을 때 `pending` 사진만 연결한다. 기존 실사·업로드 사진은 보존한다. 대체 설명과 상세의 접힌 사진 정보에 AI 생성 예시를 표시한다.
- Actions `pipeline`의 `pending_only=true`는 등록한 사진이 있는 대기 원고만 복원하고, 공식 YouTube `videos.list`로 최근 서로 다른 제작자 2명·원문 인용을 다시 확인한다. 통과 후 기존 전체 검사와 배포를 수행한다. 추가 음식 발견·AI 원고·사진 판별·상품 검색은 호출하지 않는다.
- 대기 캐시는 검사·push 전에 제거하지 않는다. 다음 정규 수집에서 실제 공개 목록과 대조해 정리한다. 하루 1회 정규 수집에서도 등록한 생성 사진을 사용한다.
- 이번 등록: 요거트 찹쌀떡·생초코 찹쌀떡·크런치 27 큐브. 생성은 대화 도구로 실행했으며, GitHub 예약 작업에 신규 이미지 자동 생성 API를 연결한 것은 아니다.

```bash
npm run pipeline -- --auto-publish --dry-run # 실제 API 키 필요. 검증 보고서만 만들고 페이지·DB는 바꾸지 않음
npm run content:check
npm run content:import -- 수집결과.json --approve # 사람이 확인한 초안 병합
npm run photos:sync
npm run photos:auto -- --dry-run # AI 키 필요. 보고서만 저장하고 사진·페이지·등록부는 보존
npm run links:auto -- --dry-run # 쿠팡·AI 키 필요. 실제 API 호출 횟수는 기록하고 공개 콘텐츠는 보존
npm run lint
npm run typecheck
npm run test:unit
npm run test:e2e
npm run test:content
```

`test:e2e`는 기존 관리자·예시 데이터 기능, `test:content`는 실제 JSON 전체와 연도 필터·사진·출처를 검사한다. 두 브라우저 검사는 같은 `out/`을 사용하므로 순서대로 실행한다. 데이터 개수를 고정하지 않아 새 음식이 추가돼도 검사한다. `test:content`를 마지막에 실행하면 공개 콘텐츠의 정적 빌드가 남는다.
